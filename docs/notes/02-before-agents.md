# How this was built before AI agents

## The classic toolbox, by pipeline stage
| Stage | Classic approach | Examples |
|---|---|---|
| Find a site's feed | Feed autodiscovery: `<link rel="alternate" type="application/rss+xml">` in the page head; guess `/feed`, `/rss`, `/atom.xml` | Every RSS reader |
| Follow sources | RSS/Atom polling; push via WebSub (formerly PubSubHubbub) | Google Reader, Feedly, Inoreader, Miniflux, FreshRSS |
| Sites without feeds | Hand-written per-site scrapers that *generate* a feed | RSSHub, RSS-Bridge, Feed43 |
| Email-only newsletters | Convert email to a feed | Kill the Newsletter |
| Detect page changes | Fetch, narrow with a CSS/XPath selector, diff | changedetection.io, Visualping, Distill |
| Scraping | HTTP client + HTML parser + selectors; real browser for JS sites | requests + BeautifulSoup/lxml, Scrapy, Selenium, Puppeteer, Playwright |
| Save requests | Conditional GET (`ETag`, `Last-Modified` → `304 Not Modified`) | Any polite crawler |
| Article text | Generic main-content heuristics (text density, link density) | Readability, boilerpipe, trafilatura, newspaper3k |
| Metadata | Page-embedded structured data | schema.org JSON-LD (`Article`, `datePublished`), Open Graph, `<time datetime>`, microformats `h-entry` |
| Visual/ML extraction | Computer vision + ML classifiers on rendered pages | Diffbot |
| Remove duplicates | Canonical URLs, URL normalization, near-duplicate hashing | `rel=canonical`, SimHash/MinHash |
| Ranking | Topic classifiers, TF-IDF, collaborative filtering | Google News, Prismatic, Zite |
| Summaries | Human curators or extractive summarization | TLDR-style newsletters, TextRank |
| Scheduling | cron / job queues, check each feed at a rate matching its update history | Celery, Google Reader's crawler |

## How stable each kind of signal is (most → least)
1. **Feeds and APIs:** a published contract; rarely break.
2. **Sitemaps:** generated by the CMS; stable.
3. **Semantic metadata:** JSON-LD, Open Graph, `<article>`, `<time datetime>`. Survives redesigns because SEO depends on it.
4. **Generic heuristics** (Readability-style): not site-specific, so a redesign rarely breaks them; imperfect.
5. **Site-specific CSS selectors:** break on redesigns, A/B tests, and hashed class names (`css-1x2y3z`, CSS modules, Tailwind builds).
6. **Positional XPath** (`/div[3]/div[2]/a`): break on almost any change.

"Scraping is brittle" is mostly about levels 5–6.

## The real danger: silent failure
A broken scraper usually doesn't crash. It returns 0 items, or the wrong field, and nobody notices. Classic mitigations:
- Validate outputs: item count > 0, dates parse, URLs resolve, titles aren't empty.
- Fallback chains: feed → JSON-LD → generic heuristic → selector.
- Alert when a source is quiet for much longer than usual.
- Shared maintenance (RSSHub's community fixes routes when sites change).

## What LLMs actually change
Brittleness has two layers:
| Layer | Problem | Do LLMs fix it? |
|---|---|---|
| **Access:** getting the bytes | JS rendering, bot protection, rate limits, paywalls, logins | **No.** An agent still needs a fetcher or browser |
| **Interpretation:** understanding the bytes | Selectors break when markup changes | **Largely yes.** Extract by meaning ("the list of posts") instead of by markup |

New problems LLMs bring: cost and latency per page, non-determinism, invented URLs/dates, prompt injection, context limits on large pages.

## The hybrid pattern: a self-healing scraper
- The **agent writes the recipe once:** feed URL, or selectors/JSON-LD path for the post list. Stored in the source profile.
- **Plain code runs the recipe** on every check: cheap, fast, deterministic.
- **Validation detects breakage** (0 items, invalid dates, sudden change in shape).
- **On failure the agent re-derives the recipe**, and the new recipe is validated before being saved.

The LLM costs something only when a source is added or breaks, not on every check.

Key takeaway: agents didn't invent new ways to *access* the web. Levels 1–4 all existed before. What changed is that the human who wrote and repaired site-specific code can now be (partly) replaced by a model.
